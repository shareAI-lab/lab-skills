# Evidence levels and cross-session loading

## Claims ledger

Record each capability with date, environment, exact executable/version, provider/model/effort, identity label, transport, test input/output hashes, tool results, exit/cleanup state, and remaining limits. No token values or credential file contents belong here.

| Evidence | What it establishes | What it does not establish |
|---|---|---|
| Official documentation/source | Advertised/version-specific contract | Installed/account behavior |
| Version/help/model probe | Binary identity and advertised local capabilities | Authorized quota or completed inference |
| Handshake | Negotiation for that transport | Prompt, tools, or business success |
| Offline mock tests | Local controller branches under fixtures | Any real provider, production isolation, or cost cap |
| Tiny real prompt | That exact model/transport/account can answer that case | Long input coverage, all tools, resume, or reliability |
| Real file/search/tool task | Verified operations/artifacts for that contract | Correct contents or permission for other effects |
| Content acceptance | Actual result meets the current goal and checks | User can access the right version |
| Accessible delivery | Verified authorized entry for the accepted version | Every original outcome is complete if other work remains |
| Detached survival | Observed process/job survives the tested disconnect | Durable recovery after reboot or provider cancellation |
| Cancel/resume/failure injection | Tested semantics for that scenario | Exactly-once billing or all faults |
| Representative workload | Acceptance of the tested workload/version | Universal production guarantee |

The source package reported 22 offline fixture tests: 14 request/protocol tests and 8 background/lifecycle tests. The controller and tests are not bundled here and were not rerun for this publication. They make no provider calls and do not prove model understanding. Treat “model says read everything,” a copied hash, and a mock coverage echo as claims, not independent coverage evidence.

## Real acceptance gate

Within explicit current authorization, establish a minimal non-sensitive prompt, approved artifact/tool task, session identity/continuation test, cancellation/reconciliation behavior, and a bounded detached workload. Preserve exact terminal events and artifact validation. Do not run a new paid experiment just because this checklist exists. Stop at auth, quota, missing approval, or ambiguous side effects; continue only safe unrelated work.

Update this evidence ledger when a real receipt arrives; do not silently promote all CLIs or effort levels based on one success. The package is a reusable workflow with offline-controller design notes, **not a claim that its external execution paths have all passed end-to-end acceptance**. Validate visible output and tool artifacts independently: reasoning-only token usage can leave an empty answer, while a real written report can still contain scientific errors. Correct existing deliverables and their entry points when findings change.

## Installed personal skill versus external harness loading

1. **Personal ChatGPT/Codex skill:** save through the personal-skills workflow and verify the reconciled active remote skill path by exact frontmatter name. This is the installation criterion. Current-session lists/UI can be cached; refresh the Skills page or discover the saved skill in a new session. Do not claim that every future conversation necessarily auto-invokes it.
2. **Native child task:** pass the resolved skill path/package explicitly in the handoff if its discovery list does not include it. Shared model intelligence does not imply shared files or automatic skill loading.
3. **External CLI reading a shared filesystem:** after confirming access is authorized, give the resolved path and request that it read the relevant instructions. Confirm accessibility; do not assume the parent machine's path exists remotely.
4. **External CLI with its own skill mechanism:** consult its current documented user/project instruction mechanism; propose a narrow deployment only if requested. Do not globally copy files, replace existing instructions, or install a plugin merely to obtain reuse.
5. **Remote harness without file sharing:** include a minimal relevant workflow excerpt plus the task contract in the permitted prompt/context bundle. Do not copy secrets or unnecessary user sources as part of “skill setup.”

The initial installation does not deploy this skill to external CLIs or modify any remote instruction files. Different harnesses may need different explicit loading mechanisms.
